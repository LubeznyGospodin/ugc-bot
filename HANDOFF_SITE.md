# HANDOFF — перенос packman-prod.ru с Tilda на код (июль 2026)

Хендофф для нового чата. Задача: **перенести весь сайт** packman-prod.ru с Tilda на
собственный кодовый сайт, задеплоить на Railway (рядом с ботом), потом перевести домен.
Работаем **фоном на staging** — боевая Tilda живёт, пока новый сайт не готов и не сверен.

---

## 0. Зачем переезжаем (контекст, не повторять ошибок)

Каталог UGC-креаторов должен наполняться **программно из бота**: креатор заполняет анкету →
админ жмёт «Разместить» → карточка появляется в канале и на сайте. С Tilda это **не работает**:
её Store API из автоматизации нестабилен (создание товара виснет, CSV-импорт кладёт товары
«редакциями» в чужой раздел, `copyproduct` не создаёт в разделе, `saveproduct` только обновляет).
Пробовали много раз — вывод: **надёжно создавать карточки в Tilda из кода нельзя**.

На своём сайте публикация = запись в БД (`published = true`), то есть проблема исчезает.
Решение принято через совет советников (см. `council-report-*.html`): **мигрировать, но не
раздувать в маркетплейс** — сначала перенести то, что есть, плюс автопубликацию.

## 2. Стек — рекомендация

**Next.js (App Router) + TypeScript + Tailwind v4, деплой на Railway, данные из существующего
Postgres.** Почему так:

- **SSG/ISR** — страницы отдаются готовым HTML: и SEO, и скорость (Tilda этого не даёт лучше).
- Каталог и карточки генерируются из БД; `revalidate` обновляет после публикации из бота.
- Tailwind — быстро собрать дизайн-систему и адаптив без CSS-каши.
- Railway — там уже живут бот и Postgres, один провайдер, приватная сеть до БД, HTTPS бесплатно.

**Про экспорт с Tilda: не тащить вёрстку.** Экспорт даёт `t-rec`-дивы, inline-стили, jQuery и
блочный мусор — дорабатывать это дороже, чем написать чисто. **Забрать из Tilda нужно только
контент**: тексты, изображения, структуру секций, SEO-тексты. Вёрстку писать заново
компонентами (это же даёт возможность «докрутить дизайн», как просил заказчик).

**Альтернатива, если хочется совсем просто:** отдавать HTML прямо из существующего Python-сервиса
(FastAPI + Jinja2) — плюс в том, что не нужен второй сервис. Минус: свой роутинг, свои мета-теги,
руками картиночная оптимизация. Рекомендация — всё же Next.js, но решение за исполнителем.

## 6. Интеграция с ботом (главная причина переезда)

Пайплайн заказчика:

1. Креатор заполняет анкету в боте → строка в Google-таблице.
2. Бот сразу собирает медиа (в т.ч. **качает с Я.Диска**, если креатор прислал ссылку) и, если
   комплект **2 фото + 4 видео**, шлёт админу альбом-превью + кнопки **[✅ Разместить] [❌ Нахер]**.
   Не комплект → метка в таблице «не хватает: видео 1/4».
3. Админ жмёт «Разместить» → бот постит в канал @ugc_creatory **и должен создавать карточку на
   сайте** ← это и появится после миграции.
4. Ссылки проставляются в таблицу: **W** (канал), **X** (сайт).
5. Догонятель: если в таблице есть ссылка на канал, а на сайт нет — добавить на сайт.

**Что нужно от сайта:** эндпоинт/механизм публикации. Простейший вариант — сайт читает Postgres,
а бот просто ставит `placement='placed'`; страница ревалидируется (ISR) или дергается
`/api/revalidate`. Тогда «создание карточки» = запись в БД, что и требовалось.

Код бота, куда смотреть: `bot/handlers/placement.py` (кнопки, публикация, метки),
`bot/sheets.py` (`report_write` — W/X, `content_status` — «Контент»).

## 7. SEO и миграция домена (не потерять трафик)

1. **Снять карту старых URL** (Tilda) → составить таблицу соответствий old → new.
2. **301** на всё, что меняет адрес; особенно `/ugc_creators/tproduct/<uid>-<slug>`.
3. Перенести `<title>` / `description` (или улучшить), сохранить H1-смыслы.
4. `sitemap.xml` + `robots.txt`, canonical на каждой странице, OG-теги.
5. Проверить в **Google Search Console**: какие страницы в индексе и есть ли органика (это же
   определяет, насколько бережно мигрировать; проверку никто ещё не делал).
6. Переключение домена — **в самом конце**, после сверки staging.
